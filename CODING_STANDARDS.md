# Стандарты кода

Документ задаёт правила для Standards-ревьюера. Применяй контекстные правила ниже и источники по ссылкам. Корневой `AGENTS.md` задаёт полномочия. Этот документ не расширяет назначение.

## Источники ревью

- Для владения доменом и терминологии читай [DOMAIN.md](DOMAIN.md), [docs/agents/domain.md](docs/agents/domain.md) и подходящие ADR.
- Для серверной и клиентской части читай инструкции приложений, когда они появятся: `apps/api/AGENTS.md` и `apps/web/AGENTS.md`.
- Для суждения о тестах читай [docs/agents/testing.md](docs/agents/testing.md) и [ADR 0012](docs/adr/0012-tests-at-public-seams-on-real-infrastructure.md). Храни правила там, не копируй сюда.
- Для инструкций, скиллов и указателей контекста читай [.opencode/skills/writing-for-agents/SKILL.md](.opencode/skills/writing-for-agents/SKILL.md) и справочник по механике скиллов, если он нужен.
- Форматирование, диагностика компилятора, ограничения импортов, расхождения сгенерированного API и механически проверяемая раскладка принадлежат настроенным проверкам. Не повторяй их диагностику как ручную находку.

## Контекстные проверки

Для изменённого взаимодействия между модулями применяй [ADR 0003](docs/adr/0003-four-modules-and-in-process-contracts.md). Разрешённый импорт не доказывает, что модуль владеет бизнес-решением или что взаимодействие только читает. При нарушении цитируй решение и фактическое поведение.

Для изменений с несколькими компаниями применяй [ADR 0002](docs/adr/0002-shared-multi-tenant-company-id.md). Проверяй, что `company_id` изолирует данные компании и что доступ не расширяется.

Для аутентификации и токенов применяй [ADR 0006](docs/adr/0006-authentication-sessions-and-agent-tokens.md). Web-сессия и токен агента не заменяют друг друга. Проверяй границу доступа.

Для тестов применяй [docs/agents/testing.md](docs/agents/testing.md) и [ADR 0012](docs/adr/0012-tests-at-public-seams-on-real-infrastructure.md). Проверяй поведение через публичный шов HTTP, а не через приватные методы, порядок вызовов и внутренние классы.

Для изменений контрактов API применяй [docs/technical-foundation/web-api-contract.md](docs/technical-foundation/web-api-contract.md). Проверяй перегенерацию OpenAPI и TS-типов.

## Находки

Сообщай правило-источник, изменённое место, условие срабатывания и последствие. Отделяй нарушения принятых решений проекта от необязательных предложений по дизайну. Общие запахи кода остаются в `code-review`. Этот документ не копирует их базу.

## Сопровождение

Используй конкретный пропущенный дефект или повторяющееся трение на ревью, чтобы предложить дополнение, уточнение или удаление. Назови наблюдаемый случай и почему существующие правила или проверки его пропустили. Для нового контекстного правила дай повод, что проверять, последствие и источник. Подтверди новую политику у владельца, прежде чем считать её требованием.

Если правило можно проверить механически, предложи lint, архитектурную или CI-проверку. Когда инструмент начал проверять правило, убери дублирующую работу ревьюера. Сохраняй один источник истины для каждого правила.
