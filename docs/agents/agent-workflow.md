# Полный путь агента

Документ описывает, как агент проходит задачу от спецификации до закрытия в трекере. Он применяется к задачам с меткой `ready-for-agent`, которые требуют изменения файлов. Метка не запускает работу. Задачи wayfinder и триажа идут по своим правилам: они закрывают решение, а не пишут код.

## Термины

Термины определены в `DOMAIN.md`.

## Условия старта

Работу запускает владелец: он явно выбирает `implement` или `implement-spec`, в том числе обычной фразой с названием скилла. Если запрос не называет ни один скилл, предложи вход и жди выбора. Метка `ready-for-agent`, issue, подготовка и комментарий ревью работу не запускают.

После выбора владельца начни, только если выполнены все условия:

- задача имеет метку `ready-for-agent`;
- в задаче есть результат и критерии приёмки;
- у задачи нет открытых блокеров;
- спецификация не противоречит `AGENTS.md`, `DOMAIN.md` и ADR, если они есть.

Если спецификация неполная или противоречивая, не начинай. Напиши комментарий к задаче, поставь метку `needs-info` и остановись.

## Шаги

1. **Прочитай задачу и спецификацию.** Прочитай issue и связанные документы. Прочитай `AGENTS.md`, `DOMAIN.md`, ADR и `docs/agents/human-review.md`, если они есть. Не расширяй объём задачи.
2. **Создай ветку.** Следуй правилу веток в `AGENTS.md`. Не работай в `main`.
3. **Реализуй изменение.** Держись спецификации. Не добавляй изменения вне спецификации.
4. **Выполни доступные проверки.** Запусти проверки, объявленные в репозитории или задаче. Для документов проверь ссылки и пути. Запиши команды и результат. Если проверка недоступна, укажи причину. Не выдавай недоступную проверку за успешную.
5. **Сделай коммит.** Сделай один логический коммит. Заголовок напиши в повелительном наклонении. Тело объясняет причину. Не коммить секреты.
6. **Проведи независимое ревью до PR.** Запусти отдельного агента-ревьюера с чистым контекстом. Он применяет `code-review` по двум осям: стандарты и спецификация. Стандарты ревьюер читает в `CODING_STANDARDS.md`, правила человеческих проверок в `docs/agents/human-review.md`. Ревьюер проверяет полноту человеческих проверок и публикует комментарий к задаче. В комментарии укажи вердикт, базу, head, проверки, человеческие проверки, блокирующие и неблокирующие замечания.
7. **Исправь подтверждённые замечания.** Подтверждённое замечание имеет доказательство. Исправь блокирующие замечания. Спорные замечания передай человеку. Ревьюер проверяет исправления и затронутые взаимодействия, без полного повторного анализа без причины. Проведи не больше двух раундов, затем решает человек.
8. **Повтори проверки и ревью.** Повтори затронутые проверки. Ревьюер проверяет всё изменение против базы. Внеси исправления в тот же коммит через amend. Не делай force-push.
9. **Открой PR.** Открывай PR после ревью без блокирующих замечаний. Создай draft PR, если результат ещё требует проверки. Переведи PR в ready только когда проверки и ревью покрывают текущее изменение. Заполни тело PR по шаблону ниже. Дай ссылку на комментарий ревью и проверенный head.
10. **Получи принятие человека.** Человек одобряет PR явно. Отдельной продуктовой приёмки нет: одобрение PR и есть принятие. Одобрение называет полный head SHA. Любой новый head, в том числе после чистого обновления из `main`, требует нового одобрения. Зелёные проверки, ревью и назначение реализации не дают права на merge. Запиши ссылку на одобрение и SHA. Если одобрение неясно, спроси владельца.
11. **Исправь замечания человека.** Замечания человека блокируют merge. Исправь их, повтори проверки и ревью, затем снова попроси одобрения. После открытия PR не переписывай историю: добавляй коммиты исправлений. Squash-merge объединит их при слиянии.
12. **Слей изменение.** Перед merge дождись успешного `ci-ok` для текущего результата PR. Незавершённые, отсутствующие, отменённые и старые успешные проверки не считаются. Не отменяй падение и не считай повторный запуск доказательством. Когда проверки зелёные и одобрение действует для текущего head, сделай squash-merge по правилам проекта. Если merge делает агент, используй `gh pr merge <number> --squash --match-head-commit <approved-sha>`. Удали ветку. Не сливай без одобрения. Не сливай при падающих проверках.
13. **Закрой задачу.** PR body содержит `Closes #N`. GitHub закрывает задачу при merge. Проверь закрытие. Если задача не закрылась, закрой её с комментарием. Сними метку `ready-for-agent` после закрытия задачи.
14. **Сообщи результат.** Напиши человеку результат, проверки, итог ревью, ограничения и конкретное действие для приёмки. Для каждой дополнительной проверки используй поля из `docs/agents/human-review.md`.

## Шаблон комментария ревью

```md
## Ревью

- База: `<commit>`
- Head: `<commit>`
- Проверки: `<команды и результат>`
- Человеческие проверки: `<полнота и ссылки на доказательства>`
- Вердикт: одобрено / есть блокирующие замечания

### Блокирующие замечания

- ...

### Неблокирующие замечания

- ...
```

## Шаблон PR

```md
## Результат

...

## Проверки

- `<команда>` — `<результат>`

## Ревью

- Проверенный head: `<commit>`
- Ссылка на комментарий: ...

## Приёмка

- Что проверить человеку: ...
- Ожидаемый результат: ...
- Доказательства и их пределы: ...

## Риски

...

Closes #N
```

## Правила

- Не пушь в `main`.
- Не меняй защиту ветки.
- Не отключай проверки.
- Не считай метку, issue или ревью разрешением начать реализацию.
- Не расширяй назначение скилла: диагноз не разрешает исправление, исследование и прототип работают только в согласованном объёме.
- Не сливай без явного одобрения человека, которое называет полный SHA.
- Не считай зелёные проверки разрешением на merge.
- Не отменяй падающую проверку и не выдавай старый зелёный прогон за текущий.
- Не закрывай задачу до merge.
- Не добавляй новые проверки в этой же задаче. Открой отдельную задачу.
- При сбое остановись. Если сбой до PR, не открывай PR. Если сбой после PR, не сливай его. Сообщи, что найдено, что неясно и какой следующий шаг. Пробел в спецификации оформи отдельной задачей.
