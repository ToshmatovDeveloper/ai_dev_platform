# Полный путь агента

Документ описывает, как агент проходит задачу от спецификации до закрытия в трекере. Он применяется к задачам с меткой `ready-for-agent`, которые требуют изменения файлов. Задачи wayfinder и триажа идут по своим правилам: они закрывают решение, а не пишут код.

## Термины

Термины определены в `DOMAIN.md`.

## Условия старта

Начни работу, только если выполнены все условия:

- задача имеет метку `ready-for-agent`;
- в задаче есть результат и критерии приёмки;
- у задачи нет открытых блокеров;
- спецификация не противоречит `AGENTS.md`, `DOMAIN.md` и ADR, если они есть.

Если спецификация неполная или противоречивая, не начинай. Напиши комментарий к задаче, поставь метку `needs-info` и остановись.

## Шаги

1. **Прочитай задачу и спецификацию.** Прочитай issue, связанные документы, `AGENTS.md`, `DOMAIN.md` и ADR, если они есть. Не расширяй объём задачи.
2. **Создай ветку.** Следуй правилу веток в `AGENTS.md`. Не работай в `main`.
3. **Реализуй изменение.** Держись спецификации. Не добавляй изменения вне спецификации.
4. **Выполни доступные проверки.** Запусти проверки, объявленные в репозитории или задаче. Для документов проверь ссылки и пути. Запиши команды и результат. Если проверка недоступна, укажи причину. Не выдавай недоступную проверку за успешную.
5. **Сделай коммит.** Сделай один логический коммит. Заголовок напиши в повелительном наклонении. Тело объясняет причину. Не коммить секреты.
6. **Проведи независимое ревью до PR.** Запусти отдельного агента-ревьюера с чистым контекстом. Он применяет `code-review` по двум осям: стандарты и спецификация. Ревьюер публикует комментарий к задаче. В комментарии укажи вердикт, базу, head, проверки, блокирующие и неблокирующие замечания.
7. **Исправь подтверждённые замечания.** Подтверждённое замечание имеет доказательство. Исправь блокирующие замечания. Спорные замечания передай человеку. Проведи не больше двух раундов, затем решает человек.
8. **Повтори проверки и ревью.** Повтори затронутые проверки. Ревьюер проверяет всё изменение против базы. Внеси исправления в тот же коммит через amend. Не делай force-push.
9. **Открой PR.** Открывай PR после ревью без блокирующих замечаний. Заполни тело PR по шаблону ниже. Дай ссылку на комментарий ревью.
10. **Получи принятие человека.** Человек одобряет PR явно. Отдельной продуктовой приёмки нет: одобрение PR и есть принятие. Замечания человека блокируют merge. Исправь их, повтори проверки и ревью, затем снова попроси одобрения. После открытия PR не переписывай историю: добавляй коммиты исправлений. Squash-merge объединит их при слиянии.
11. **Слей изменение.** После одобрения сделай squash-merge по правилам проекта. Удали ветку. Не сливай без одобрения. Не сливай при падающих проверках.
12. **Закрой задачу.** PR body содержит `Closes #N`. GitHub закрывает задачу при merge. Проверь закрытие. Если задача не закрылась, закрой её с комментарием. Сними метку `ready-for-agent` после закрытия задачи.
13. **Сообщи результат.** Напиши человеку результат, проверки, итог ревью и ограничения.

## Шаблон комментария ревью

```md
## Ревью

- База: `<commit>`
- Head: `<commit>`
- Проверки: `<команды и результат>`
- Вердикт: одобрено / есть блокирующие замечания

### Блокирующие замечания

- ...

### Неблокирующие замечания

- ...
```

## Шаблон PR

```md
## Результат

...

## Проверки

- `<команда>` — `<результат>`

## Ревью

Ссылка на комментарий: ...

## Риски

...

Closes #N
```

## Правила

- Не пушь в `main`.
- Не меняй защиту ветки.
- Не отключай проверки.
- Не сливай без явного одобрения человека.
- Не закрывай задачу до merge.
- Не добавляй новые проверки в этой же задаче. Открой отдельную задачу.
- При сбое остановись. Если сбой до PR, не открывай PR. Если сбой после PR, не сливай его. Сообщи, что найдено, что неясно и какой следующий шаг. Пробел в спецификации оформи отдельной задачей.
