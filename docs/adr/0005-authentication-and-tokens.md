# Аутентификация, сессии и токены агента

Frontend — React SPA. Backend — ASP.NET Core API. Сервис общий для нескольких компаний. Сценарии S1, S4 и S6 требуют входа, токена агента и мгновенного отзыва доступа.

## Решение

Web-вход:
- HttpOnly-cookie с серверной сессией в PostgreSQL.
- Один origin: Nginx проксирует `/api` в production, Vite proxy в разработке.
- CSRF-защита через antiforgery-токен.
- Сессия живёт 7 дней без активности и 30 дней максимум.
- Пароли хешируются встроенным `PasswordHasher<Employee>` на PBKDF2.
- Приглашение живёт 7 дней, одноразовое, в базе хранится хеш.
- Сброса пароля в MVP нет.

Компания:
- Slug компании стоит в пути: `/acme/login`, `/acme/projects`.
- Сессия хранит `company_id`.
- Slug служит только для поиска компании, не для авторизации.
- Один сотрудник принадлежит одной компании.

Токен агента:
- Несколько opaque-токенов на сотрудника.
- Префикс `agt_`, случайные 32 байта, в базе SHA-256.
- Срок 90 дней, ручной отзыв, последнее использование.
- API агента только для чтения: проекты, репозитории, инструкция.
- Агент не может приглашать, создавать проекты, менять участников и деактивировать.

Доступ агента к GitHub:
- Агент использует личные учётные данные сотрудника: SSH, `gh`, credential manager.
- Платформа отдаёт только URL репозиториев и инструкцию.
- Платформа не выдаёт GitHub-токен агенту.

## Причины

- Серверная сессия отзывается сразу при деактивации.
- Один origin убирает CORS и ограничения third-party cookies.
- Opaque-токен проще отзывать, чем JWT.
- Личные данные GitHub сохраняют правило «агент не шире сотрудника».
- Несколько токенов поддерживают будущих нескольких агентов.

## Последствия

- Запрос в БД на каждый вызов API.
- Нужна очистка старых сессий.
- Нужна CSRF-защита.
- Агент не выполняет разрушительные действия.
- Облачные агенты позже потребуют отдельного токена GitHub.
- Сброс пароля появится позже.
