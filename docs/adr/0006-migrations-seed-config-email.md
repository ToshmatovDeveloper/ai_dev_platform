# Миграции, стартовые данные, конфигурация и email

В проекте несколько модулей со своими схемами PostgreSQL. Первая версия обслуживает одну компанию. Приглашения приходят по email.

## Решение

Миграции:
- One-shot сервис `migrate` в Docker Compose.
- Образ API запускается с командой `--migrate`.
- Сервис применяет миграции всех модулей по порядку и завершается.
- API стартует после успешного завершения `migrate`.
- Команда идемпотентна.

Стартовые данные:
- Команда `--seed` создаёт одну компанию и приглашение для первого сотрудника.
- Команда печатает ссылку-приглашение.
- Первый сотрудник задаёт пароль по ссылке.
- Пароль не хранится в конфигурации.
- Команда идемпотентна.
- Конфигурация: `Seed__CompanySlug`, `Seed__CompanyName`, `Seed__FirstEmployeeEmail`.
- В примерах используется slug `acme`.

Конфигурация:
- `.env` для Docker Compose.
- `appsettings.*.json` для несекретных настроек.
- `dotnet user-secrets` для локального запуска API.
- `.env.example` хранится в Git, `.env` не хранится.
- Ключ GitHub App монтируется файлом.
- В production используются Docker secrets или secret manager.
- Секреты не попадают в Git и логи.

Email:
- SMTP и MailHog локально.
- Приглашение отправляется через outbox с повтором.
- UI показывает ссылку-приглашение как запасной путь.
- В production подойдёт любой SMTP-провайдер.
- Привязки к конкретному email-сервису нет.

## Причины

- Явный шаг миграций не создаёт гонку при нескольких экземплярах API.
- Seed через приглашение не хранит пароль в конфигурации и переиспользует S1.
- Разделение `.env`, `appsettings` и user-secrets держит секреты вне Git.
- Outbox не блокирует приглашение при сбое почты.
- MailHog упрощает локальную проверку писем.

## Последствия

- В Compose появляются сервисы `migrate` и `mailhog`.
- Первый вход требует ссылку-приглашение.
- Если письмо не дошло, ссылку можно скопировать из UI.
- В production нужны SMTP-настройки.
- Seed выполняется один раз на окружение.
- Сброса пароля в MVP нет.
