# Контракт API агента

Агент — внешний клиент. Он подключается по личному токену сотрудника и готовит рабочее окружение. Ему нужны только разрешённые проекты, репозитории и инструкции.

## Решение

Один endpoint:
- `GET /api/agent/v1/bootstrap`.
- Авторизация: `Authorization: Bearer agt_...`.
- Версия стоит в пути.

Ответ содержит:
- компанию: `id`, `name`, `slug`;
- проекты: `id`, `name`, `instruction`;
- сервисы: `id`, `name`;
- репозиторий: `fullName`, `sshUrl`, `httpsUrl`.

Правила:
- API только для чтения.
- Возвращаются только проекты, где сотрудник состоит участником.
- Нет пагинации в MVP.
- Нет endpoint для отчёта о проверке доступа.
- Агент сам проверяет GitHub и сообщает результат сотруднику.
- OpenAPI-схема публикуется.

Ошибки:
- `401` — токен неверный или истёк.
- `403` — сотрудник неактивен.
- `404` — проект недоступен или не найден.

## Причины

- Агенту нужны все данные для подготовки окружения. Один вызов уменьшает число запросов и частичных состояний.
- `fullName`, `sshUrl` и `httpsUrl` позволяют агенту выбрать локальный способ доступа.
- Версия в пути защищает внешний контракт.
- Чтение не даёт агенту менять людей, проекты и токены.
- Платформа не хранит результаты проверки доступа, которых нет в требованиях MVP.

## Последствия

- Ответ растёт вместе с числом проектов. Для MVP это допустимо.
- Позже можно добавить список и детали проекта.
- Позже можно добавить телеметрию проверок доступа.
- Агент обращается к API через публичный origin платформы или напрямую в разработке.
- OpenAPI-схема становится частью контракта для внешнего агента.
